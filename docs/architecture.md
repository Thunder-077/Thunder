# Thunder 架构设计

## 整体架构

Thunder 采用 **Web First + 模块化** 的架构设计，是一个面向个人的模块化应用平台。

```
┌─────────────────────────────────────────┐
│              Thunder App                │
│  ┌───────────────────────────────────┐  │
│  │          App Shell                │  │
│  │  ┌──────┐ ┌──────┐ ┌──────────┐  │  │
│  │  │Sidebar│ │Topbar│ │  Content  │  │  │
│  │  └──────┘ └──────┘ └──────────┘  │  │
│  └───────────────────────────────────┘  │
│  ┌───────────────────────────────────┐  │
│  │        Module Registry            │  │
│  │  ┌─────┐ ┌─────┐ ┌─────┐        │  │
│  │  │Mod A│ │Mod B│ │Mod C│  ...   │  │
│  │  └─────┘ └─────┘ └─────┘        │  │
│  └───────────────────────────────────┘  │
└─────────────────────────────────────────┘
```

## 为什么 Web First

1. **最低门槛**：浏览器是最通用的运行环境，无需安装即可使用
2. **快速迭代**：Web 技术栈成熟，开发调试效率高
3. **跨平台基础**：Web 应用可以轻松包装为 PWA 或桌面应用
4. **渐进增强**：从 Web 开始，逐步增加离线、桌面等能力

## 为什么预留 PWA / Tauri

- **PWA**：提供离线访问、安装到桌面、推送通知等能力，是 Web 应用的自然增强
- **Tauri**：当需要原生系统能力（文件系统访问、系统托盘、全局快捷键等）时，Tauri 可以将 Web 应用包装为轻量桌面应用，相比 Electron 体积更小、性能更好

当前阶段只做 Web，但架构设计确保未来可以无缝迁移。

## 模块化边界

### 主应用职责

- 应用外壳（Shell）：布局、导航、主题
- 模块注册与发现
- 全局设置
- 通用组件库
- 路由管理

### 模块职责

- 独立的功能单元
- 通过 Manifest 声明元信息
- 自包含的 UI 和逻辑
- 不直接依赖其他模块

### 数据边界

- 模块间不共享状态
- 模块数据通过独立 key 存储
- 模块间通信通过事件或主应用中转（未来）

## 项目结构

```
thunder/
├── apps/
│   └── web/                    # Next.js 主应用
│       ├── src/
│       │   ├── app/            # App Router 页面
│       │   ├── components/     # 应用组件
│       │   │   └── ui/         # shadcn/ui 组件
│       │   ├── hooks/          # 自定义 hooks
│       │   └── lib/            # 工具函数和配置
│       └── ...
├── packages/
│   ├── core/                   # 核心类型和模块系统
│   ├── config/                 # 共享配置
│   └── ui/                     # 共享 UI 组件（预留）
├── docs/                       # 设计文档
└── modules/                    # 独立模块（预留）
```

## 未来扩展方向

1. **模块独立包**：将模块拆分为独立 npm 包，支持动态加载
2. **插件系统**：第三方模块通过插件 API 接入
3. **数据同步**：端到端加密的跨设备数据同步
4. **Tauri 桌面端**：利用 Tauri 提供原生系统能力
5. **PWA 离线**：Service Worker + IndexedDB 实现离线可用
